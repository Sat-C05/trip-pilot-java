# Phase 3: structured extraction and evidence validation

Research now assembles durable backend-validated results, including explicit unavailable fields and missing requirements. The frontend planning experience remains Phase 4. Initial discovery still covers Wikivoyage guides, not whole-web search or provider inventory.

## Result API and persistence

Authenticated `GET /api/research/jobs/{jobId}/result` returns the owner's result. Another owner receives 404. A queued/running, cancelled, interrupted or legacy job without a result returns 404 `RESULT_NOT_READY`. Acquisition failures also store explicit gap results. Migration V5 adds an immutable result per job, joined through the existing context/owner foreign key. Result insertion, validation event and terminal job state commit atomically under the worker ownership/cancellation lock. Late model output cannot publish after cancellation or restart fencing.

The result contains validator version, requirement revision ID, validation time, completeness, missing requirement names, seven field records, safe decision codes, a deterministic duration estimate and a cost-estimate gap reason. Field names are DESCRIPTION, STAY, TRANSPORT, ACTIVITY, PRICE, AVAILABILITY and POLICY. Every field is present, even when no candidate was returned. Missing departure, destination, dates, travelers, budget and currency remain explicit. No defaults are guessed. Complete means all required inputs and all fields are supported; current guide-only research normally finishes PARTIAL / VALIDATED_WITH_GAPS.

## Extraction and support

New jobs snapshot `extractive-v2`, which runs without tools and proposes only field, exact quote and passage UUID. The backend binds destination, ISO arrival/departure dates, travelers and currency from the captured requirement revision before normal scope/evidence validation; the model cannot overwrite them. This removes unnecessary scope copying and its null/extra-object failures without accepting invented facts. It cannot submit URLs, source IDs, estimates, scope objects, tool calls or authority claims. Unknown/duplicate keys, trailing JSON, invalid types/UUIDs and oversized arrays/text fail strict parsing. Whole-response fences have only the bounded lossless repair described below. Captured `extractive-v1` jobs retain the strict eight-key legacy proposal parser with model-supplied scope validation; older unsupported versions fail explicitly. Historical records are never rewritten.

Input selection scans saved passages for complete guide sentences, up to 500 characters, for description/stay/transport/activity topics. It favors relevant guidance over opening navigation and historical hotel mentions; singular and plural category terms are recognized. Initial ALL research makes separate focused calls for description and guide topics that have eligible evidence. The v2 prompt contains the destination, explicit topic, three-key output example and selected source excerpt; dates/travelers/currency/origin/budget/preferences stay backend-owned and are not duplicated into the prompt. Calls share the unchanged snapshotted turn/deadline budget, global single repair and application inference slot. Missing topic evidence does not trigger a futile model call. Fallback previews are used only when no eligible guide sentence is found. A UTF-8 byte ceiling retains 512 framing tokens and captured output reserve; the adapter also checks actual token/context/output limits. Source text stays untrusted data and production raw model output never enters diagnostics.

Validation requires a passage from this job actually supplied on that successful extraction call; exact offsets/text in the saved source; an exact, bounded, nonblank quote inside supplied text; requirement scope (guide destination name ignores letter case; other values are exact); and nonfuture retrieval time. Destination must appear in the source title and quote, or a whole source-passage sentence may use a destination article as context: its title must begin with the exact destination followed by a district slash, title separator or guide label, and the saved article body must independently name that destination. Partial phrases and title-only inconsistent documents cannot use this alternative. This establishes document scope rather than semantic entailment; reviewers still assess meaning and suitability. Different snippets from one passage/calls retain their exact supplied text, so subsequent topics do not discard previously supported excerpts. No genuine citation can support a paraphrase or an invented value merely because its source ID exists. Category/instruction/volatile checks remain mandatory.

SUPPORTED means an attributed exact guide excerpt with `ATTRIBUTED_EXCERPT_SEMANTICS_UNVERIFIED`. It does not prove source truth, geographic identity, semantic entailment, safety of travel advice or completeness of conflict detection. Keyword/injection detection is heuristic; it is not a universal semantic security classifier. There are no model action tools to execute injected instructions. Downstream UI must display attributed excerpts, states and limitations, rather than turn these records into stronger claims.

## Freshness, alternatives and estimates

Guide fields expire using the captured description window (default 30 days). Retrieval time describes when this immutable text was fetched, not when its publisher last updated a fact. Stale excerpts retain citations with no accepted value. Result reads conservatively downgrade supported/conflicting fields to STALE when their captured freshness window expires; the stored historical revision and validation timestamp remain unchanged. A new job is needed to refresh evidence.

Different accepted excerpts for the same field retain all alternatives as CONFLICTING with a null value and `DIFFERING_EXCERPTS_REQUIRE_REVIEW`. This is intentionally conservative: complementary wording can also require review. The backend does not majority-vote, resolve semantic contradictions or claim to find every conflict in omitted passages. Old rejected/stale evidence cannot silently become current support.

PRICE, AVAILABILITY and POLICY require provider evidence tied to dates, traveler/room/product scope and observation time. General guides do not supply that contract, so these fields remain UNAVAILABLE / NO_SCOPED_PROVIDER_EVIDENCE, even if they contain numbers or starting prices. The snapshotted 6-hour price, 15-minute availability and 7-day policy windows are available for future authoritative adapters; freshness alone never confers authority.

Duration is ESTIMATED only when both dates exist in valid order. The backend computes calendar-day difference and records both inputs, requirement revision and the explicit overnight-stay assumption; it does not invent hotel check-in rules or transport nights. Without dates it is unavailable. Monetary totals are unavailable with NO_VALIDATED_NUMERIC_PRICE_INPUTS. No guessed unit costs, currencies or multipliers enter arithmetic.

## Bounds and failures

Schema errors receive at most one tool-free repair across the entire job, charged as another model turn. The bounded previous output is untrusted and the repair asks to preserve valid fields; repaired candidates undergo every support check again. Semantic failures do not trigger a model rewrite into acceptance. Invalid repair, context/output limits, runtime failure, deadline and exhausted budgets yield explicit gaps and safe codes.

When DESCRIPTION is unavailable, stale or conflicting, the backend may make one targeted `destination + travel guide` search, subject to remaining search/page/model/deadline budgets. Only newly discovered URLs are fetched, at most three per pass; retry extraction uses newly acquired evidence. Initial acquisition plus retry uses at most two searches, six guide-page fetches (optional metadata is separately charged within the same page cap) and nine model calls (four topics per acquisition plus the one global repair), further reduced by captured limits. Unsupported volatile fields do not cause futile inventory searches. Queries exclude dates, traveler identifiers, preferences and chat history.

Events allowlist counters, timings, versions, repair flags, validation completeness and support/gap counts. They omit raw query/page/prompt/model bodies and rejected claims. Public results contain accepted/stale/conflicting known-source excerpts and safe decision codes, not raw model proposals. Sources remain separate from conversations.

Destination-only research uses article content rather than Wikivoyage banner navigation, table of contents or indicator widgets. Evidence previews shrink within the conservative context budget; only the exact supplied preview can support a citation. Extraction instructions show the complete candidate object shape and distinguish unknown travel details from unsupported guide facts. Guide destination scope permits letter-case differences (mumbai/Mumbai); different names and all other scope values remain strictly checked. This does not change booking scope. A whole-response Markdown JSON fence can be removed losslessly within the existing one-repair budget; its inner object must still pass the unchanged strict parser and support checks. Invalid inner JSON uses the normal bounded model repair instead. Prose, arrays, extra fields and partial JSON are never salvaged.

Long guides exceeding the saved-text character cap retain a short introduction and bounded Get in/Get around/See/Do/Sleep sections at whole-sentence boundaries, rather than only the opening history/district text. Hashes and passage offsets are computed after this selection; earlier snapshots are immutable. Topic selection excludes generic district-directory accommodation descriptions and weather/best-time-to-visit statements as stay/activity guidance. Filled labels alone are insufficient verification: inspect accepted public excerpts for substantive content.

## Verification and local handoff

Run `scripts/verify-phase3.ps1 -Smoke` with trusted-project PowerShell setup from README and the existing project MySQL on 13306. It creates a generated temporary schema/account, runs all five migrations and the complete Maven suite against that schema, starts a dedicated one-model/one-slot Ollama on free port 11437, builds both Java modules, and optionally runs packaged backend/demo/frontend HTTP smoke. It deletes only its generated schema/account and temporary credential files afterward. Other services, the application database and MySQL80/3306 are preserved. `-ModelPort` chooses another free verification port; the application's model default remains 11436. The helper preloads the pinned model before starting JVMs and bounds verification heaps to leave room for inference. Teardown captures only owned runner children and rechecks executable/start time before stopping them. Originally absent environment entries are removed explicitly; an empty inherited endpoint cannot suppress smoke startup defaults. Sufficient available RAM/pagefile remains necessary for the pinned model.

`-DatabaseOnly -TestSelection 'EvidenceValidatorTest,ValidationDatabaseTest,ResearchDatabaseTest,FoundationDatabaseTest'` runs focused database/validator checks without launching a model. The real-model fixture is skipped in that mode unless explicitly enabled; do not treat it as full live acceptance. Default verification enables all database, internet and local-model flags. The live synthetic cases exercise usable extraction, malicious instructions, wrong destination and stale evidence through the production repository/executor/adapter. The real Jaipur job checks stored citations, explicit volatile gaps, counters, scoped result API and SSE. Deterministic fixtures cover malformed/fake/unsupported evidence, scope/dates/travelers/currency/room schema, conflicts, timestamps, context capacity, repair/turn limits, inaccessible/empty sources, cancellation and safe diagnostics.

Restart the backend to load current extraction changes and `extractive-v2` / `validation-v1` defaults. Captured v1 jobs retain their legacy protocol; unsupported older versions fail with UNSUPPORTED_PROMPT_VERSION. Submit new research/refresh to capture v2. Old snapshots/evidence remain preserved. Phase 4's historical acceptance is recorded separately; phases 1–5 are now complete and Phase 6 still needs authorization.
